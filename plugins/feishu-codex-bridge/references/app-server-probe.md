# App Server read-only capability boundary

This reference defines the only admissible App Server experiment: a bounded,
owner-requested, read-only capability probe. It is not a Bridge backend, a
Desktop producer, a responder client, or an activation path. The current Bridge has
one admitted isolated `beeper` local producer; App Server is not
part of it and must never supplement, replace, or recover that route.

## Current conclusion

Capability is evaluated latest-first against the exact current independent Codex
CLI and a freshly generated matching Schema. The source-only auditor can confirm
reviewed protocol shapes, while the bounded host can inspect a minimal live
read-only path. Neither result certifies production routing.

The current host cannot immutably bind the serving `codex_app` instance to the
separately supplied source bytes. A completed protocol core therefore still ends
closed with `runtime_provenance_unavailable`, `static_inputs_bound=true`,
`runtime_source_bound=false`, and overall `bound=false`.
`desktop_task_coordination_certified` and `activation_allowed` remain false.
This is a capability boundary, not a reason to add an SDK, App Server writer, or
another fallback route.

## Admission and ownership

Each probe requires one explicit owner request and one-attempt authority. Before
launch, the controlling Bridge project task must verify all of the following:

- the exact independent native CLI and its hash;
- a fresh Schema generated by that CLI and a passing static contract audit;
- a fresh, empty, absolute, non-reparse probe directory;
- the Bridge is stopped and both Bridge queue layers have zero nonterminal work;
- every retired producer surface remains non-executable and untouched; and
- one controller owns one hard-time-bounded stdio child and its complete process
  tree.

The controller must not read, copy, print, persist, synthesize, or return
`CODEX_APP_TOOLS_PIPE_PATH`. An ambiguous launch, disconnect, timeout, or shutdown
consumes the attempt and is not replayed.

## Exact read-only sequence

The protocol core in `scripts/app_server_mvp.py` may perform only this sequence:

1. `initialize`, then `initialized`;
2. one `thread/start` with `ephemeral=true`, `sandbox=read-only`, and no model
   turn;
3. bounded, cursor-checked `mcpServerStatus/list` discovery for `codex_app`;
4. `mcpServer/tool/call` for `list_threads(limit<=50)`; and
5. `mcpServer/tool/call` for `list_projects`.

The App Server-owned control-thread ID exists only in memory to bind those calls
and to prove that the control identity is absent from the returned Desktop task
catalog. Every returned task and project must have one unique, non-empty ID before
the corresponding boolean may become true. IDs, titles, project labels, catalog
contents, paths, MCP text, native channel material, and remote errors are discarded.

Every request shares one absolute deadline across write, response, and notification
reads; notifications never extend it. A transport unable to enforce the supplied
remaining timeout is outside the contract.

## Host and receipt contract

`scripts/app_server_host.py` validates the exact executable and static digests,
starts one suspended child, assigns it to a private kill-on-close Job Object, and
only then resumes it. No-write/no-delete handles pin the probe directory and static
inputs through owned-child shutdown. Before releasing those handles, the host
rechecks directory identity, emptiness, reparse state, and every digest.

The result is one ASCII-only, answer-free JSON object containing only fixed enums,
booleans, counts, and fixed issue tokens. It always reports
`queue_claimed=false`, `responder_mutation_attempted=false`,
`read_only_desktop_task_coordination_attested=false`, and
`activation_allowed=false`. A closed `failure_phase` plus monotonic safe-partial
booleans may identify only boundaries already completed; it never contains native
errors or private values. Missing channel, MCP, caller identity, tools, malformed
results, or deadline is classified as `desktop_task_port_unavailable` without a
fallback.

## Absolute no-second-client boundary

The Beeper is an identity anchor for read-only MCP calls, never a writer for
a Desktop-owned responder. The probe must never:

- call `thread/resume`, `turn/start`, archive, or `thread/compact/start` using a
  Desktop responder ID;
- call `send_message_to_thread` or any mutating/approval-gated task tool; its
  current prompt approval declaration is not automation authority;
- claim queue work, change bindings, create/restore/compact responders, arm responder
  callbacks, or
  contact Feishu;
- let Bridge, CLI, App Server, SDK, database, rollout, named pipe, deep link, UI,
  OCR, clipboard, or transcript extraction become another responder client; or
- reconstruct or export the transient Desktop channel.

The separately admitted exact-UUID Beeper cold-load deep link is not an App
Server probe capability: it loads only the registered Beeper, carries no
payload, never names a business responder, and cannot transport a final.

The read-only probe starts no model turn, so it needs no compaction. If a later
separately designed Beeper owns model turns, it may compact only itself via
`thread/compact/start`. Raw `/compact` text is not the native protocol operation and
must never be aimed at a Desktop-owned responder.

## Static audit and bounded invocation

Regenerate Schema from the exact current CLI, then audit only the supplied files:

```powershell
python scripts/app_server_contract.py `
  --schema-root <fresh-protocol-directory> `
  --desktop-mcp-manifest <desktop-mcp.json> `
  --desktop-mcp-server <server.mjs> `
  --json
```

A static pass means only that the reviewed current shapes still exist, including
`mcpServer/tool/call`, required thread ownership fields, transient channel
declaration, native tool forwarding, and the approval-gated task-tool declaration.
It never launches a process or proves which source serves a live call.

Only after the admission checks may the separately authorized owner invoke the
bounded host:

```powershell
python scripts/app_server_host.py `
  --codex-executable <exact-native-codex.exe> `
  --expected-codex-sha256 <preflight-sha256> `
  --probe-cwd <fresh-empty-directory> `
  --schema-root <fresh-protocol-directory> `
  --desktop-mcp-manifest <desktop-mcp.json> `
  --desktop-mcp-server <server.mjs> `
  --hard-timeout-seconds 45 `
  --json
```

These commands document the audited surface; they are not standing authority to
run it. The owner task must stop only its own child and may retain only the closed,
answer-free receipt.

## Adapting to newer Codex releases

On a Codex update, regenerate Schema and inspect capabilities and shapes rather than
branching on old version numbers. If a required shape changes, fail closed and adapt
the single current implementation. Do not retain the replaced adapter as an
executable compatibility path.

If the product later exposes immutable runtime-source identity, define and validate
a new closed provenance contract before drawing a stronger conclusion. Do not
reinterpret an older receipt, relax responder ownership, or attach App Server to a
Desktop-owned responder.
